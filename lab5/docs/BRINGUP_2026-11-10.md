# Lab 5 Nucleo bring-up — November 10, 2026

We flashed the two NUCLEO-F401RE boards on the existing powered Lab 3 CAN
setup. N2/front is ST-LINK `066BFF485270535067124020` with `swap_ab`;
N3/rear is `066BFF505487525067171333` without the swap. We have not started
the matching Lab 5 Pi application in this session or completed timing checkoff.

## Faults found and changes

- Repeated state requests replayed the complete uncommitted suffix. With a long
  history this consumed MCU time repeatedly. We now maintain a separate pending
  graph, rebuilding it on boot or suffix replacement. The public graph still
  changes only after majority commit.
- Duplicate successful APPEND acknowledgements could each trigger another
  catch-up transmission. We now send the next entry only when the peer's matched
  index advances; periodic retries still recover lost messages.
- A Nucleo leader recounted the whole held-event backlog every 20 ms while the
  Pi was absent. We now count the Pi-acknowledged committed prefix incrementally.
  Unchanged backlog queries do not reread flash.
- Earlier repeated elections filled the 508-slot term/vote journal. We observed
  watchdog resets and full journals. The firmware now reclaims a full journal
  before starting the application watchdog, retaining entries, term and vote.
  The new bank is activated last. **Runtime erase/truncation timing is still
  unresolved:** this startup recovery does not make a running sector erase meet
  the timing limits. The watchdog remains enabled at one second.
- Boot output now records reset cause, and CAN diagnostics include controller
  error counts from the last state-change callback. Debug queue draining is
  bounded per pass so it cannot indefinitely postpone committed-entry output.

The LED pin assignments were not changed. See [pin identification](PINS.md).

## CAN-indicator follow-up

The team reported that disconnecting N3 from A lit the A indicator on both
Nucleos, with N2's indicator briefly clearing. The same happened on B. All
connections were then restored. The Pi process listing showed the old Lab 3
`cockpit.py`, not `cockpit5.py`; no matching three-node Lab 5 baseline existed.

The restored-link capture in `logs/lab5/20261110-flash/restored-173137/`
shows both boards at term 513, leader N2, commit 1768, `nodes=0x6`,
`links=0x3c`, both DEG outputs zero and `ctrl_seen=0`. Neither board had a
fresh N1 heartbeat. Transmit rejections, receive drops and controller
state-change counts did not increase between the captured diagnostic rows.
The printed error counts are from the last state-change callback, not live
register measurements. This short observation does not clear earlier faults.

The source and new host regressions explain a plausible cause: with no wheel
input since startup, the legacy Pi sends no CTRL or heartbeat, but sends BLINK
about every 500 ms. After N3 leaves A, N2 has no other frequent sender on A;
its local 60 ms silence detector lights A, clearing briefly on each BLINK.
The LED describes traffic received locally, not which physical jumper was
removed. This reproduction is not a capture of the team's physical fault.

The team's subsequent three-second filtered Pi capture corroborates the
traffic explanation: it contains six successive BLINK (`0x200`) updates about
500 ms apart on both buses, with some duplicate copies, and no `0x100` N1
heartbeat or `0x010` CTRL. This was captured with links restored, not during
the cut. The old process belongs to the system service
`team4-lab3-cockpit.service`; stop that service for the Lab 5 transition rather
than killing a PID that its service manager may restart. Pi Python is 3.13.5,
and Git/GCC are installed; the Pi-native Lab 5 build is still pending.

`test_bus_indicators.py` compiles the production MCU zone monitor and feeds it
actual simulated Lab 5 packets. With the matching Pi active but wheel input
absent, cutting either Nucleo's A or B link lights only that node's affected
indicator; restoration clears it. A separate legacy-Pi regression reproduces
the other node's flicker. All **74 host tests pass**. Firmware, thresholds and
pin assignments were unchanged in this follow-up; no reflash was performed.

## Faults found and changes

- Repeated state requests replayed the complete uncommitted suffix. With a long
  history this consumed MCU time repeatedly. We now maintain a separate pending
  graph, rebuilding it on boot or suffix replacement. The public graph still
  changes only after majority commit.
- Duplicate successful APPEND acknowledgements could each trigger another
  catch-up transmission. We now send the next entry only when the peer's matched
  index advances; periodic retries still recover lost messages.
- A Nucleo leader recounted the whole held-event backlog every 20 ms while the
  Pi was absent. We now count the Pi-acknowledged committed prefix incrementally.
  Unchanged backlog queries do not reread flash.
- Earlier repeated elections filled the 508-slot term/vote journal. We observed
  watchdog resets and full journals. The firmware now reclaims a full journal
  before starting the application watchdog, retaining entries, term and vote.
  The new bank is activated last. **Runtime erase/truncation timing is still
  unresolved:** this startup recovery does not make a running sector erase meet
  the timing limits. The watchdog remains enabled at one second.
- Boot output now records reset cause, and CAN diagnostics include controller
  error counts from the last state-change callback. Debug queue draining is
  bounded per pass so it cannot indefinitely postpone committed-entry output.

The LED pin assignments were not changed. See [pin identification](PINS.md).

## Console export fix and live verification

The original `lab5 log` handler held the protocol mutex while printing the
entire history. A slow UART must not hold up consensus processing. We now take
a fixed committed-end snapshot, read each immutable entry briefly under the
mutex, and release it before printing. BEGIN/END markers identify a complete
export; a failed storage read emits LOG_ERROR instead of silently skipping it.
`lab5 network` similarly copies its fields before printing.

Live exports also exposed mixed characters from concurrent diagnostic prints
and shell output. All application diagnostics and commands now use the shell's
UART writer once it is active; startup retains a printk fallback. A separate
application-only print mutex was insufficient because shell echo used another
writer. The four new host tests exercise the production handlers' lock
boundaries, fixed export endpoint during concurrent appends, error reporting,
and use of the shared shell output path. All four passed, and both builds passed.
This is additional targeted coverage after the earlier 74-test run, not a new
claim that the whole suite was rerun.

launcher mode without legacy Lab 3 test controls. The team confirmed that both
ERR LEDs turned off and automatic hazards stopped. The dual-Nucleo recording
in `logs/lab5/20261110-flash/wheel-input-183222/` shows matching COCKPIT_OK at

captured network snapshots stayed in term 517 with N1 leader and graph
`0x7/0x3f`; later diagnostic samples show valid controls and zero throttle/brake.
Thus the first wheel transition passed, but stable operation was not yet proved.

The Pi's application log is
`~/.local/state/team4-lab5/20261110-174835/events.csv`. The team's read-only
analysis of its latest 120 seconds reported 5993 accepted-update rows,
14 inter-update gaps of at least 100 ms, and a maximum gap of **139.354 ms**.
These are application-observed update intervals, not kernel packet-arrival
timestamps. The existing 100 ms input deadline was not changed. The Windows
observer reported no send gap of at least 60 ms in the inspected log, but this
alone cannot locate every delay in the network/application path.

The Pi reported Wi-Fi power saving on. A requested passive capture could not
run because tcpdump was not installed; its zero-row file is a failed capture,
not evidence of no traffic. Five existing wheel-observer tests passed;
the Lab 5 launcher's diagnostic timeout label now says 100 ms, which changes
only the message and not the transmitted packet or Pi policy.

After the team disabled Wi-Fi power saving and verified it off, a new
50-second application-log window contained 2500 accepted updates, eight gaps
of at least 100 ms, and a maximum gap of **142.802 ms**, with eight ERROR/OK
pairs. The windows differ in length, so their raw gap counts are not directly
comparable. Power saving off did not eliminate the problem. Packet-arrival
capture is still needed to separate network delays from application delays.
The later Windows log contains one 78.0 ms sender gap; that running GUI still
uses the earlier 80 ms diagnostic label. Neither this one observation nor the
application logs establish where every delay occurred.

The independent Nucleo recording in
`logs/lab5/20261110-flash/wheel-powersave-check-183823/` starts with N2 leading

and three NODE_1_DOWN/UP cycles (1985/1987, 1991/1993, 1997/1999), each followed

confirmed that the Pi program and CAN wiring were untouched during this run.
These are unintended availability changes, not deliberate fault-test results
or proof of a Wi-Fi cause. The protocol's discovery REPORT continues even
when wheel input is stale, so loss of wheel input alone should not remove N1.

Code review found that the inherited once-per-second STATUS print still ran
in the Pi control loop despite the other console output using a background
writer. STATUS now uses that existing nonblocking queue. New STATE_CAUSE rows
preserve the input age, latch, consensus and queued-CAN snapshot at transitions.
TICK_SLOW rows report receive, agent-update, transmit and output-phase elapsed
times when a tick takes at least one nominal 20 ms wheel period. These times
include operating-system delays; they are not CPU execution times or measured
WCET. Persistence synchronization and the 100 ms input deadline are unchanged.

All **81 Lab 5 host tests** and **five wheel-observer tests** passed after these
changes. The new Pi status/timing changes are locally tested but have not yet
been deployed to the running Pi, and no live fix is claimed for the input gaps.
